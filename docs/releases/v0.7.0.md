Two findings of a cross-vendor audit of the chain of runs (tracking #57), fixed in one change (#58). A trusted receipt key in an input profile is now held to the curve, so a malformed pin can no longer authenticate a forged acquisition; and `verify-run` holds a run's retained answer to its signed audit record, so a signed, witnessed export can no longer carry a different answer beside a successful report. Nothing in the store, the chain of runs or an export's bytes changes; a run that verified under `v0.6.0` verifies the same, unless its export was altered.

## What an operator must do

- **Check your input profiles' trusted receipt keys before updating.** An installation whose profile pins a public key that is not the canonical encoding of a point on the curve (or is a point of small order) now refuses to start, with a message that names the key. Such a key was never a Gateway's: a normally generated key passes. Releases and verification exports that froze such a profile no longer run or verify until the profile is replaced and reviewed.
- **Nothing else.** The chain of runs, the store's schema, the export versions and `verify-run`'s exit codes are unchanged.
- **A program that reads `verify-run`'s report** sees one new refusal, `audit-disposition-mismatch` (the CLI says `differs-from-audit`), and `retainedDisposition` now says `matches-audit` where the comparison passed, in place of `not-checked`.

## Trusted receipt keys are held to the curve (#58, closes #52)

A mapping profile's trusted receipt public key was checked only as 32 bytes of lowercase hex. With the identity point as the pin, a signature of that point followed by zeros authenticated a fabricated response, and preparation accepted it as a `record` fact. The key is now parsed with the same checks Runner applies to its own record signatures — a canonical encoding, a point on the curve, not of small order — on every path a trusted key enters: service start, `verify-run --profiles`, every input preparation (releases read back from the store included) and `--public-key`; the parsed key is what receipt verification uses.

## A run's retained answer is held to its signed record (#58, closes #53)

Runner's signature covers the audit record's exact bytes; it never covered the export's `run.result`, and ordinary verification never compared the two, so an export with only its answer changed passed `--require-signed --require-witnessed` with a successful report. `verify-run` now compares the retained `run.result.disposition` with the disposition inside the signed audit record before either input path and independently of the optional `--runtime` replay; a missing or null answer is refused, a difference fails with `audit-disposition-mismatch`, and a second member whose name differs from `disposition` only by case (which a struct reader elsewhere might take instead) is refused as well. `--help` and MAPPING-V2 now name every export member the signature does not cover.

## Desk

Desk's Jobs record checks the chain of runs with the runtime's verifier and passes no key; it is not affected by this release, and the audit's third finding (#54: a key replaced at its path after Desk's start signs later runs under a key Desk's list does not name) stays open on both sides (Desk #345).

## What each part establishes, and does not

A run's signature establishes that a holder of Runner's key signed the audit record's exact bytes, and now that the export's retained answer is that record's answer; it does not establish anything about the export's other members (named in `verify-run --help`), the correctness of a calculation, the truth of an input, or the time the run was prepared (#55, open). A trusted receipt establishes that the named Gateway key signed the acquisition, as far as the pinned key is that Gateway's; a malformed pin is now refused rather than trusted.
