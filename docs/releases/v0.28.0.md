# v0.28.0

Runner v0.28.0 carries three changes since v0.27.0. Shared mapping-v2 preparation gets three
fixes found by the workflow admission experiment (#200, #201). Workspace and input roots
are now strictly UTF-8 (#202, #203). Tests and a design section show that selected
preparation runs beside a full ordinary profile registry (#190, #205). The first two
change what the Runner accepts, and some hosts and exports that worked with v0.27.0 are
refused by v0.28.0, as set out below. The companion pins do not move. The Spec's maturity
remains `draft`. This release claims no Extended Runner support.

## Breaking changes

- **`adapter-http` query form (#201).** A dialect whose `adapter-http` operation sends a
  `query` that is not an object of string templates is now refused `profile-mismatch`.
- **Exports that omit retained inputs (#201).** `verify-run` now refuses an export whose
  run leaves out its retained `facts` or `evidence`. This includes exports of dialect runs
  with no evidence target that v0.27.0 or earlier evaluated.
- **Paths outside UTF-8 (#203).** A boot line, a direct Go host or a relocation that gives
  a path that is not valid UTF-8, has an unpaired surrogate escape, or contains NUL is now
  refused. Before this release such a path was replaced with U+FFFD, or, for NUL, kept. A
  store whose input root binding is not valid UTF-8 or contains NUL no longer opens.

## What an operator must do

- **Fix `adapter-http` queries.** A job whose saved release holds a non-conforming
  `adapter-http` query fails every new run before acquisition. Re-preview the dialect with
  an object `query` of string templates, such as `{"query":{"q":{"$param":"query"}}}`,
  and release again.
- **Keep the earlier Runner for exports it cannot verify.** v0.28.0 cannot verify exports
  of dialect runs with no evidence target that v0.27.0 or earlier evaluated. This includes
  such runs still in the store that are exported after the upgrade. To verify them, keep
  the earlier Runner or re-run them.
- **Refuse non-UTF-8 roots in the host.** Raw-byte roots are not supported, and there is
  no byte-exact relocation route. A host whose source root is not valid UTF-8 must refuse
  it before it creates a workspace or queues a relocation.
- **Re-create a workspace whose binding holds NUL.** No operation rewrites a stored
  binding that is outside the rule. A binding with NUL never named a usable directory, and
  no relocation can name it, so the only route is a new workspace.
- **Check a binding that holds U+FFFD.** Such a binding still opens. It is flagged as
  described below. If its root does not exist, the binding may have been made from a path
  that lost bytes.
- The usual care applies before any upgrade: stop Desk and Runner and back up the Jobs
  workspace, including SQLite/WAL, as
  [State and backups](../../README.md#state-and-backups) describes. The store schema is
  unchanged and there is no migration.

## Shared preparation fixes (#200, #201)

These three fixes were found by the workflow admission experiment (#146, which does not
merge). They are carried here without its workflow code.

### The derived evidence document always reaches the Runtime

A version-2 or version-3 dialect preparation now always passes both derived documents
to the Runtime, including an empty evidence-availability document, `{}`
(spec/dialect.md §8.1). Before this release, a preparation with no evidence target was
evaluated with no evidence, and its audit record kept `"evidence":null,"evidenceSupplied":false`.
It is now evaluated with `evidence: {}` and `evidenceSupplied: true`. Verdicts do not
change: the Runtime reads an omitted evidence document and `{}` the same way. A version-1
file mapping is not a dialect preparation and keeps its optional evidence.

For such dialects, API clients see:

- `/v1/inputs/preview` and `/v1/jobs/{job}/triggers/preview` return `evidenceText: "{}"`
  where they returned `""`.
- `/v1/inputs/next` returns `evidenceText: "{}"` where it left the member out.
- `/v1/previews` has no `evidenceText`. Its `sample.evidence` is now `{}` where it was
  absent.

### `adapter-http` query templates are held to the dialect

Under a profile whose `adapter.name` is `adapter-http`, an operation's `query`, when
present, must be an object of string templates (spec/dialect.md §4.1). It must not be a
template form itself. Each member must be a string, a `$text`, or a `$param` of type
`string` or `timestamp`. The parameters in scope are the case's and the source's own. A
whole `$param` or `$text`, a string, `null`, an array, or an object with a non-string
member or an integer `$param` is refused. Other `http`-shaped adapters are not held to
this rule.

The refusal code is the existing `profile-mismatch`. The new messages, each prefixed by
`source <name>: `, are:

- `adapter-http query must be an object of string templates`
- `adapter-http query must not be a template form`
- `adapter-http query member <name> must be a string template`

The same check, `profileRequestForm`, runs at preview, before acquisition, at every
preparation, and in `verify-run`. It also runs when a saved release is frozen into a
workflow, for every stage, unused stages included. At freeze it also refuses an MCP
request that names a tool its profile does not allow. The workflow writer is private: no
route reaches it in this release. `openapi.json` (`MappingSource.arguments`) and
[MAPPING-V2](../MAPPING-V2.md) state the rule.

### Verification refuses retained inputs that are not the derivation

After the lineage comparison, `verify-run` compares the run's retained `facts` and
`evidence` with the verified derivation, as JSON values. The only new refusal is for an
omitted member: `retained facts or evidence do not match verified derivation`. The export
is refused, not repaired. A retained input that is present and differs, `null` included,
was already refused, with `supplied facts differ from the verified derivation` or
`supplied evidence differs from the verified derivation`. That is unchanged. Exports whose
retained members are only reordered still verify. Every export checked in to this
repository derives at least one evidence target and still verifies.

## Workspace and input roots are strictly UTF-8 (#202, #203)

Runner now refuses a path it cannot represent exactly. The rule covers:

- the boot line's `dir`, `workspace`, `runtime` and `inputRoot`;
- the same members of a direct Go host's `runner.Config` (`runner.Open`);
- a relocation's `dir`, `workspace`, `previousInputRoot` and `inputRoot`, through
  `relocate-workspace` and `runner.RelocateWorkspace`.

Each must be valid UTF-8 with no NUL. Before this release, the boot line was decoded with
`encoding/json`. That turned an invalid byte or an unpaired surrogate escape into U+FFFD,
which names a different path. A NUL from a decoded <code>&#92;u0000</code> was accepted.
A direct Go host could also pass raw bytes or NUL. A relocation request's raw invalid
byte or unpaired surrogate escape was already refused, but only as the generic "invalid
relocation request". For relocation, this release replaces that message with the named
codes below, and adds the NUL, Go API and stored-binding refusals. Only the path members
listed here are checked. Other boot members, such as `signingKey` and
`executorOwnership.root`, are not, though the whole boot line must still be valid UTF-8.

Each refusal ends with its code in parentheses, and none creates or records anything:

- `request-not-utf8`: the boot line or relocation request is not valid UTF-8. This is
  checked before decoding.
- `path-unpaired-surrogate`: a path member has a `\u` surrogate escape with no matching
  pair. Every spelling of the member that `encoding/json` would match is checked, at
  every occurrence.
- `path-not-utf8` and `path-contains-nul`: a path given to `runner.Open` or
  `runner.RelocateWorkspace` is not valid UTF-8, or contains NUL (including a decoded
  <code>&#92;u0000</code>). These name the member, not its value.
- `stored-binding-not-utf8`: the store's input root binding is not valid UTF-8. Only a
  direct Go host could have stored one.
- `stored-binding-contains-nul`: the store's input root binding contains NUL. A direct Go
  host could have stored one, and so could a boot line before v0.28.0, from a decoded
  <code>&#92;u0000</code>.

Both stored-binding refusals show the binding with its bytes escaped (`%q`). Runner does
not guess the original. Before this release, such a store was refused with the generic
"runner store belongs to another owner, workspace or schema" whenever the boot line named
another root, and opened when it named the same one. Now open and relocation both refuse
it by name, whatever the boot line names. A store whose `workspace` identity holds NUL
from such a boot line is refused at boot (`path-contains-nul`), since the boot line must
name it.

**A binding that holds U+FFFD.** A binding that is valid UTF-8 with no U+FFFD opens and
relocates as before, with no change in output. A binding that holds U+FFFD also opens.
Runner cannot tell a literal U+FFFD from one that replaced a lost byte, so it flags the
binding instead:

- `GET /v1/status` reports `inputRootReplacementCharacter` and `inputRootExists` whenever
  an input root is bound. The second says whether the bound root exists as a directory.
  Neither member appears without an input root. `openapi.json` (`Status`) carries both.
- At start, `serve` writes one line to standard error when the binding holds U+FFFD:
  `runner: the inputRoot binding "..." contains U+FFFD, which may stand for a byte lost
  before the path reached Runner; the bound root exists` (or `does not exist`).
- A Go host reads the same from the new `Service.InputRootBinding()`.

Exact source and destination identity, the prior-binding comparison, operation-ID replay,
and retained run, release and audit bytes are unchanged. A literal U+FFFD in a valid path
still round-trips byte for byte. The README section
[Paths are UTF-8](../../README.md#paths-are-utf-8) states the rule.

## Selected preparation beside a full ordinary registry (#190, #205)

This release changes no runtime code for #190. The selected-profile namespace from
v0.27.0 (#191, contract `selected-profile-preparation/1`) already meets its need. Two new
tests run that host. One has 15 configured profiles plus the installed ordinary
generated-input profile, with an ordinary run held in the executor. The other has
ordinary profiles that together exceed `profilesBytes`. The tests pin each boundary
refusal byte for byte. A new section of
[selected-profile preparation](../design/selected-profile-preparation.md), "A full
ordinary registry", gives the answer: what counts as full, what the host does, and what
stays as it was. #190 stays open until Desk accepts it.

## Known and not fixed

- Raw-byte workspace and input roots are not supported, and there is no byte-exact
  relocation route (#202).
- No operation rewrites a stored input root binding that is outside the UTF-8 rule.
- The workflow writer that freeze checks is private. No route reaches it.
