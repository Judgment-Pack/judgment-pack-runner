Runner now keeps a chain over the runs it completes, and can have each run's audit record signed with the installation's key. Two new export versions carry them, and `verify-run` checks both. A chain or a signature establishes nothing against the operator on its own: the chain needs a checkpoint held by someone else, and the operator holds the signing key. Nothing `v0.4.0` accepted is refused unless it is asked for, with one exception: a run whose Runtime leaves its audit trail in a shape Runner cannot keep exactly now fails.

## What an operator must do

- **Nothing, to keep things as they are.**
  - Verification exports are version 2 unless a later version is asked for. Versions 2 and 3 are byte for byte what `v0.4.0` made.
  - `verify-run` reports version-2 and version-3 exports byte for byte as before.
  - Without `signingKey` in the boot line, nothing is signed.
  - On first start, the store gains the chain's table. Runs recorded before then are never given an entry.
- **A run whose audit trail is not one line ended by a newline now fails.** Before, such a trail was accepted if it parsed. Released Runtimes write one line, so with them nothing changes. See [the chain of runs](#a-chain-of-the-installations-runs-34-closes-30).
- **To make the chain mean something against the operator:**
  - take a checkpoint, from a version-4 export or the last entry of `GET /v1/run-chain`;
  - give it to someone who holds it apart from you;
  - check later runs against it with `verify-run --chain <file> --expect <held checkpoint>`.

  `--require-witnessed` refuses a run that no held checkpoint covers.
- **To have runs signed:**
  - the release's Runtime must sign. That is Runtime `v0.26.0` or later;
  - make an Ed25519 seed, for example with that Runtime's `jpack audit key`;
  - name it in the boot line as `signingKey`. The path must be absolute, contain no link, lie outside Runner's state directory, and name a file only its owner, Runner's user, can read or write. Runner refuses to start with a key placed otherwise;
  - check runs with `verify-run --public-key <hex>`, giving the key as `jpack audit key public` prints it. Add `--require-signed` to refuse a run that no valid signature covers.
- **A program that reads `verify-run`'s report must allow for new members on version-4 and version-5 exports:** `runChain` for both, and `signature` for version 5. A run the chain or signature checks refuse exits 1, before any re-execution, with the status `chain-invalid`, `unwitnessed`, `signature-invalid`, or `unsigned` (under `--require-signed`).
- **Desk cannot yet fetch versions 4 or 5, or the chain.** Desk asks Runner for version 3 and does not forward `GET /v1/run-chain`, and the boot line Desk writes has no `signingKey`. Until Desk changes, read them from Runner's own API.

## A chain of the installation's runs (#34, closes #30)

Each attempt has its own audit directory, never reused, so the Runtime's trail inside it holds one record and says nothing about the installation's history. Runner now keeps a chain of its own.

- **One entry per completed run.** Each entry binds the run's id to the SHA-256 of its audit record's exact bytes (`run.auditBytes`, kept since `v0.4.0`). Entries are chained by the Runtime's rules: `trail`, `sequence`, and `previous` over the exact bytes of the entry before ([runtime ADR-0047](https://github.com/Judgment-Pack/judgment-pack-runtime/blob/v0.26.0/docs/adr/0047-make-a-decision-record-defensible.md)). The checkpoint is the Runtime's own, so the Runtime's `jpack audit verify --trail --expect` reads Runner's chain too.
- **Where it lives:** the `run_chain` table in the store's SQLite database. It is backed up and restored with the rest of the store ([State and backups](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.5.0/README.md#state-and-backups)).
- **When an entry is written:** in the same transaction that records the run completed. A failed append fails the completion, and the dispatcher stops as on any storage error. Failed, interrupted and expired runs get no entry.
- **A trail Runner cannot keep exactly:** an evaluation whose audit trail still parses, but is not the record's one line ended by a newline, is refused and its run fails. There are no exact bytes for the entry to bind.
- **Export version 4** (`?version=4`) is version 3 plus a `chain` member: the run's entry, in base64, and its checkpoint. A run recorded before this release is exported as version 3 or 2, byte for byte as before.
- **`GET /v1/run-chain`** serves the whole chain, in pages.
- **A run removed from the store keeps its entry,** and its verification export answers `410 run_not_held` with the entry's sequence.
- **`verify-run`, for version 4:** the entry must name this run and the SHA-256 of the exported bytes, and the checkpoint must be the entry's.
  - `--chain <file>`: every line is an entry at its own sequence, of one trail, linked to the exact bytes of the line before, and no run is named twice.
  - `--expect <file>`, repeatable: each held checkpoint must match.
  - `--require-witnessed`: a run no held checkpoint covers is refused.
  - The report's `runChain` member gives the scope of what was checked: one supplied entry, one supplied chain, or a held checkpoint.

## Signed audit records (#37, closes #36)

A Runtime given a signing key appends a line to `signatures.jsonl`, beside its trail, for each chained record. The line signs the record's trail, its sequence and the SHA-256 of its exact bytes, with Ed25519 (runtime ADR-0047 §2b).

- **The key reaches the Runtime as `JPACK_SIGNING_KEY`,** in the environment of each operational evaluation only. Validation, locks, rehearsals and saved tests never get it. A release's frozen configuration is unchanged, and so is its digest.
- **Runner never opens the key,** and never logs or stores its path. It checks only where the key is, at start-up. The Runtime checks the key again as it opens it.
- **Runner keeps the attempt's sidecar exactly,** newlines included, as `run.auditSignatures`, in the same transaction as the record's bytes and its entry.
  - No sidecar, or an empty one, means unsigned. That is not an error.
  - A sidecar that is not private, is a link, or is over 16 KiB fails the run.
  - `GET /v1/runs/{run}` shows it; run lists and briefs leave it out.
- **Export version 5** (`?version=5`) is version 4 plus `run.auditSignatures`. A run without a sidecar is exported as version 4, or earlier, whatever is asked.
- **`verify-run --public-key <hex>`** checks the signature by the Runtime guide's rule, "Record signatures, exactly", written from the rule and importing nothing from the Runtime.
  - The key is checked before the export is read. Small-order and non-canonical keys are refused, because Go's `crypto/ed25519` accepts forged signatures under them.
  - The report's `signature` member has the status `signed`, `unsigned`, `invalid` or `not-checked`.
  - `--require-signed` refuses a run that no valid signature covers.
- **A record rewritten with its chain entry, but not re-signed,** is refused as `signature-record-mismatch`. The chain alone cannot catch that; the signature does.

## What this release does not establish

- **Anything against the operator, from the chain alone.** One supplied entry, or one supplied chain, is consistent with whatever the operator wrote alongside it. Only a checkpoint held by someone else shows that runs up to it were not rewritten.
  - The chain does not show when a checkpoint was made, or that it was held apart.
  - It shows nothing after the last held checkpoint.
  - It shows nothing about runs that were never recorded.
- **Anything about runs recorded before this release.** They have no entry and are never given one.
- **Anything against the operator, from a signature.** It shows that whoever held the key signed these exact bytes as the attempt's record. The operator holds the key, and a signature shows nothing once the key is copied.
- **That the key stays where Runner checked it.** Runner checks the key's path, owner and mode at start-up only.
- **What `v0.4.0` did not establish** still holds: that an input is true, or that a parameter's request chose the right record ([v0.4.0's notes](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.5.0/docs/releases/v0.4.0.md#what-this-release-does-not-establish)).
- **That it works with Runtime `v0.25.0`.** CI tests `v0.26.0`; the suite was also run by hand against `v0.25.0` and `v0.24.0` while the changes were built.
- **That the release runs on every platform.** The `darwin/amd64` archive is built and read, but nothing runs it. No release check starts `jpack-google-relay`.
- **That a released program starts a job.**
  - The archive checks start no job, since a released program needs Runtime and a boot line to start one.
  - CI's tests start jobs from source, within the test's own process.
  - Nothing here tests the exchange of the boot line with Desk.

[docs/releasing.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.5.0/docs/releasing.md) says how a release is made and what each check does not establish.
