Three additions and one correction of what a report says. A store, a boot line and a mapping that `v0.1.1` accepted are accepted the same; nothing new happens unless it is asked for.

## What an operator must do

- **Nothing, to keep things as they are.** `requireTestedReleases` is off unless the boot line sets it; `verify-run` re-runs nothing unless it is given `--runtime`; a trigger token reads nothing unless a caller asks.
- **Expect `verify-run` to be stricter about an export.** An export must now be exactly what Runner encodes, and the members verification relies on are read by their exact names. An export that Runner wrote is verified as before, including one written by `v0.1.0` or `v0.1.1`. An export another program re-encoded, or one carrying two members whose names differ only in case, is now refused.
- **The store gains one table** (`occurrence_keys`), created on start when it is missing. Occurrences accepted before this release have no recorded token, so no token can read them.

## `verify-run` says what it checked, and can check the disposition (#16, #17, closes #10)

`verified-inputs` checked a retained run's inputs and never read its disposition, so an export whose inputs were intact and whose disposition had been changed was reported as verified.

- The report now says so: its JSON gains `"retainedDisposition": "not-checked"`, and standard error says that the disposition was not checked.
- Given the release's own Runtime executable, `--runtime /absolute/path/to/jpack` checks the disposition too:
  - Runner hashes the executable and refuses it unless its digest is the one the release froze, and it runs the copy it hashed.
  - It evaluates the verified inputs again as a declared rehearsal, in a private directory it removes, and refuses an answer that is not labelled a rehearsal or that left an audit entry behind.
  - It compares the canonical disposition with both the retained result and the retained audit record. Only a completed run is checked.
  - When they agree it reports `verified-disposition`. When they differ it exits 1 and reports `disposition-differs`.

`verified-disposition` says the release's Runtime, given the run's inputs again, decides what the record says. It does not say the inputs or the policy are true. `verified-inputs` keeps its meaning.

## An installation can refuse jobs from untested releases (#18, closes #11)

With `"requireTestedReleases": true` on the boot line, creating a job from a release whose tests are `not-run` is refused: 409 `release_untested`, a refusal of its own beside `release_not_ready`. This applies to creation with a first trigger too, and leaves no job, trigger or revision behind. It refuses creation only. A job made before the setting was on keeps running, and repeating its creation returns it. Runner does not report the setting in `/v1/status`; whoever writes the boot line knows it.

## A trigger token can read the result of the occurrence it created (#19, closes #13)

`GET /v1/triggers/trg_<id>/occurrences/occ_<id>`, with the owner bearer and `X-Trigger-Token`, answers:

- the occurrence's `id` and `state`;
- once it has a run, the run's `state`;
- once the run is `completed`, its `disposition` and `handoffTarget`;
- nothing else: no inputs, no identifiers of runs, jobs or releases, no problem text, no listing.

The read is bound to the token that created the occurrence. Runner records that token's digest when it admits the occurrence. A token that is not its trigger's current credential gets 401 `invalid_trigger_token`. A current token asking for an occurrence it did not create gets 404 `occurrence_not_found`, the same answer as for one that does not exist. Desk does not expose this read yet.

## A security policy (#15)

`SECURITY.md` names the private route for reports. GitHub's private vulnerability reporting is on for this repository.

## What a release carries

Four archives, for Linux and macOS on `amd64` and `arm64`. Each holds `jpack-runner`, `jpack-source-worker`, `jpack-google-relay`, `openapi.json` and the licences. Windows is not released: it compiles, and nothing tests it.

To verify a download:

```sh
sha256sum --check --ignore-missing checksums.txt
gh attestation verify <archive> \
  --repo Judgment-Pack/judgment-pack-runner \
  --signer-workflow Judgment-Pack/judgment-pack-runner/.github/workflows/release.yml \
  --source-ref refs/tags/v0.2.0
```

On macOS use `shasum -a 256 --check --ignore-missing checksums.txt`. The releasing guide, linked below, has the form of the second command that holds a download to the commit as well.

## What this release does not establish

- That `--runtime` runs the bytes it hashed against a file swapped between the hash and the run. It runs the copy it hashed; no test swaps the file in between.
- That a token read racing a rotation of that token is refused. The check is one statement that requires both the current and the recorded credential; no test interleaves a rotation with a read.
- The `darwin/amd64` archive is built and read, and run by nothing. `jpack-google-relay` is started by no release check.
- The archive checks start no job: a released program needs Runtime and a boot line to start one. CI's tests start jobs from source, within the test's own process. Nothing here tests the exchange of the boot line with Desk.

[docs/releasing.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.2.0/docs/releasing.md) says how a release is made and what each check does not establish.
