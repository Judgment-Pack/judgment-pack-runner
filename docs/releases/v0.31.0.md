# v0.31.0

Runner v0.31.0 lets a Runner be run as a service that other programs call. It can start
from a configuration file on a fixed address and check a signed caller identity (#214,
#236). A job can be fixed to an opaque scope identifier that its records carry and that
listings filter by (#237). A job can carry a retry policy for a throttled source, and an
interrupted run can be retried explicitly (#238, #219). A finished run states its counts,
a failed one its error class, and listings filter by both (#239, #217).

A Runner started as before, with jobs that use none of this, keeps its store's schema
and its records' bytes, with two exceptions set out below: the journal entry of a run's
end is now `entryVersion` `"5"` in every store, and three listing answers change. The Spec's maturity remains `draft`. This
release claims no Extended Runner support.

## Compatibility

| With | What holds |
|---|---|
| A store written by v0.30.0 | Opens with no migration and stays at its schema until a job is created under a scope (schema 5) or a retry policy is first used (schema 6). |
| A Runner of v0.30.0 or earlier | Refuses a store at schema 5 or 6. Going back needs a copy of the store from before it was raised. It serves a caller's journal actor as `{"kind":"caller"}` without issuer or subject. |
| Journal readers | An entry's `entryVersion` is the highest its members call for: `"2"` a caller actor, `"3"` a scope, `"4"` an attempt, `"5"` run results. **The entry of a run's end (`run.completed`, `run.failed`, `run.interrupted`) and of a failed or expired occurrence is `"5"` in every store**, also one that uses no other feature of this release. Every other entry without those members keeps `"1"` and its bytes. |
| Judgment Pack Gateway | A retry policy takes effect for a throttled source only with a Gateway that answers it `429` or `503` in its own error form: Gateway `v0.27.0` or later. An earlier Gateway answers `400`, which is never retried. A scope identifier has the same form in both, so one identifier works on a job and on a Gateway platform. |
| Judgment Pack Runtime | Unchanged from v0.30.0: Core `0.5.0` packs need Runtime `v0.44.0` or later. |
| Desk | Not pinned by this release; Desk adopts it in its own lane. |

## Breaking changes

For a Runner started as before, two things (#243).

**The journal entry of a run's end has `entryVersion` `"5"`** and carries `counts` and
either `disposition` or `errorClass`; a failed or expired occurrence's entry carries
`errorClass` at `"5"`. A journal consumer that accepts only `"1"` must accept `"1"` to
`"5"`. `docs/design/activity-journal.md` states the whole rule.

**Three listing answers that were silently permissive now refuse:**

- A filter value that does not decode answers `400`. It was ignored before, so the
  listing answered every run.
- `outcome` on the jobs listing answers `400`. It was ignored before.
- An unknown `kind` on a journal route answers `400`. It was ignored before.

A caller that sent any of these received an unfiltered listing and must now send a valid
filter or none.

## What an operator must do

- **Nothing, to keep running as before.** Stop Desk and Runner and back up the Jobs
  workspace before the upgrade, as
  [State and backups](../../README.md#state-and-backups) describes.
- **Back up before the first scoped job and before the first retry policy.** Each raises
  the store's schema one way: schema 5 on the first job created under a scope, schema 6
  on the first use of a retry policy. No earlier Runner opens the store afterwards.
- **To run as a service,** write a configuration file outside the state directory, held
  to the signing key's file rules, and start `jpack-runner serve --config <absolute
  path>`. An address off loopback needs both a caller identity and the acknowledgment
  that the Runner terminates no TLS: put TLS in front.
- **With a caller identity configured, every control API client sends a signed token.**
  The token replaces the owner bearer on the whole control API. `X-Trigger-Token` is
  unchanged.
- **A key change needs a restart.** The key set file is read once at start.
- **For retries of a throttled source, run Gateway `v0.27.0` or later.**

## Service mode and caller identity (#240; closes #214, #236)

- **Start.** `jpack-runner serve --config <absolute path>` reads no standard input, stops
  on SIGINT or SIGTERM, and prints the same readiness line.
- **Configuration file.** Bounded in size. `listen` is required in canonical form, and
  port 0 is refused.
- **Caller identity.** A signed token (RS256, ES256 or EdDSA; the algorithm comes from
  the key) is checked against the key set file: issuer, audience, listed subject, expiry.
- **Recording.** The caller is recorded as `run.requestedBy` in the form
  `<issuer>#<subject>`, which also scopes idempotency keys. An issuer containing `#` is
  refused. The journal actor is `{"kind":"caller","issuer","subject"}` at `entryVersion`
  `"2"`.
- **Health.** `GET` and `HEAD /v1/health` need no credential and return only
  `{"healthy":…}`, in service mode only.
- Design note: `docs/design/service-mode.md`.

## A scope identifier (#241; closes #237)

- `POST /v1/jobs` takes an optional `scope`. A job keeps it for good.
- The job's triggers, occurrences, runs and every journal entry about it carry `scope`.
  A scoped journal entry has `entryVersion` `"3"`.
- Every route takes the query parameter `scope`. A request that names a record of a
  scoped job must name its scope. A different scope, none, or a scope named for an
  unscoped record answers exactly as for a record that does not exist, and journals
  nothing. A route that names no record refuses `scope`.
- `GET /v1/jobs`, `/v1/runs` and `/v1/events` filter by `scope`, exact byte match.
- Scheduled occurrences and workflow starts inherit the job's scope.
- Design note: `docs/design/scope-identifiers.md`.

## Retries (#242; closes #238, #219)

- **A retry policy fixed on a job:** `retry` with `maxAttempts` (1 to 10, default 1 as
  before), `backoffSeconds` and `maxBackoffSeconds` (1 to 3600). It governs an
  occurrence's acquisition attempts.
- **What is retried.** Only an answer of `429` or `503` in the Gateway's own error form,
  and only when no earlier call of the attempt was answered. A failure whose effect is
  uncertain is never repeated.
- **`Retry-After`,** in seconds or as a date, raises the wait. A wait above the cap, or
  past the occurrence's deadline, ends the occurrence with `retry-wait-too-long`; it is
  not shortened. At the limit the occurrence ends with `attempt-limit-reached`.
- **The wait is stored** as `nextAttemptAt` and survives a restart. An attempt in flight
  at a crash is closed as interrupted and is not tried again on its own.
- **`POST /v1/runs/{run}/retry`** with `{"attempt": n}` retries an interrupted run. It is
  the same run, and the interrupted attempt is kept in `attempts`. Refusals: `409`
  `attempt_mismatch` and `run_not_retryable`.
- **Journal.** The kind `occurrence.retry-scheduled`, and `detail.attempt` at
  `entryVersion` `"4"`.
- **Under the manual-admission gate** a retry, a retry policy and a scope are refused
  `409` `manual_profile_unsupported`. Earlier documents of this repository named the
  code `manual_unsupported`; the code never answered that.
- Design note: `docs/design/retries.md`.

## Run results (#243; closes #239, #217)

- **Counts on a finished run:** `sources` (absent when the run had no preparation),
  `decisions`, `byKind` and `byOutcome`. Runs finished before this release and
  unfinished runs have none. A retry clears them.
- **`errorClass`** on a failed or interrupted run and on a failed or expired occurrence,
  from a closed list: `source`, `preparation`, `evaluation`, `configuration`, `limit`,
  `interrupted`, `internal`. A completed run has none.
- **Journal.** The entry for a run's end carries `counts` and either `disposition`
  (`kind`, `outcomeId`) or `errorClass`. A failed or expired occurrence carries
  `errorClass`. Only those entries are at `entryVersion` `"5"`.
- **Filters.** `outcome=` and `errorClass=` on the runs listings and `kind=` on the
  journal routes, at most 10 values each. They combine with every other filter, the
  scope included, before paging.
- The status route lists the capability `run-results`. There is no store schema change
  and no new route.
- **Following finished runs.** The journal is the stream a consumer follows. This
  release adds no push. `docs/design/run-results.md` says what a push would need.

## What this release does not establish

- **A scope is a label and a filter, not an authorization boundary.** Any admitted
  caller can list everything and can name any scope.
- **No TLS.** The Runner terminates none.
- **Still one Runner per store.** Service mode does not make two Runners on one store
  safe.
- **Jobs and triggers gain no requester member.** The journal names who created or
  changed them.
- **Not exercised by a test:** the configuration file's owner checks and a bind to an
  address off loopback, which need a second user and a second interface.
- **A retry must follow the end of the Runner's whole process tree (#252).** A Runtime
  that outlived a Runner killed outright can still write its trail after a retry of
  the same run has started, leaving two Runtime-signed trails for one run. The
  Runner's record and the chain of runs hold one. A supervisor that ends the whole
  control group on a restart avoids it.
- **A store at schema 5 or 6 cannot be prepared for the manual-admission gate,** whose
  preparation takes only a store at schema 3.
- **Retries were tested against a stub** that answers in the Gateway's error form, not
  against a released Gateway.
- **Paging over a source is not in this release.** A job performs the acquisitions its
  input mapping names.
- **No conformance claim for Core `0.5.0`,** as in v0.30.0.

## Known limitations

The limitations listed in the [v0.29.0 notes](v0.29.0.md#known-limitations) stand.

Pre-release review: clean room over v0.30.0 to the head of #243, on how the four changes

order of first use; filters across scopes; secrets in the journal). No HIGH finding. One

date, corrected in this release's notes pull request with three smaller documentation
findings. One finding is filed as #252. The record is on that pull request. Same vendor,
