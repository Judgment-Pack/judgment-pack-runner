Runner v0.17.0: two more conformance rules from the dialect companion, a source parameter's pointer held to exactly a fact target and one gateway source admitted under two profiles of different classes, and two recorded vectors of an acquired dependent source, for forty-one in all.

## What an operator must do

- **Nothing for existing runs.** Exports, the journal, `verify-run`'s report, its exit codes and refusal flags are byte-identical to v0.16.0's for every existing run; all thirty-nine published vectors recompute byte for byte, and the two new ones beside them.
- **If a dialect's source parameter reads below a fact target** (for example `/sponsor/id` under the target `/sponsor`), it is now refused at the dialect's form check, before any acquisition, as the specification's reader refuses it; point the parameter at the target itself.
- **If an installation holds one gateway source under two profiles**, one `generated` for a research source's web capability and one `record` for an operation, it is now admitted; each binding takes its profile's class, the release freezes both profiles, and a release missing either, or with a changed profile, is refused as before.

## A source parameter's pointer is exactly a fact target (#111, closing #106)

- `validateDialect` records each earlier source's fact targets and `checkParams` refuses a `pointer` that is not exactly one of them, on versions 2 and 3, at submission, preview, import and `verify-run`, with the parameter and the pointer named; the case parameter's rule is unchanged.

## One gateway source under two classes (#112, closing #100)

- The check that refused "one trusted source cannot have conflicting output classes" is removed, as the dialect companion's §5.1 states a class is a profile's per binding; every path reads profiles by id and digest and none by key, source and authority; two profiles of one class stay admitted and a repeated id stays refused; `targetsByClass` and each lineage entry's `class` follow the binding.

## Two vectors of an acquired dependent source (#109, closing #107)

- `acquired-dependent-source` and `acquired-dependent-source-unknown`: the skipped-source mapping with `sponsor`'s record naming a sponsor, so `endorsement` is acquired with both parameters carried into its request, its claim `resolved` or `unknown`, and its lineage entries carrying `dependencies` in parameter order, as RFC 0018 round 12 states for every source that declares a source parameter; the thirty-nine earlier vectors were written again byte for byte by the same generator run, and the specification's reader recomputes both.
