A correction of `v0.1.0`. It fixes the fault that release was published with, and changes nothing else that Runner does.

## What an operator must do

Install it in place of `v0.1.0` if a job's mapping has two or more operation sources and runs unattended, on a schedule, a file change, an event or a cloud trigger. Such a run was refused by `v0.1.0`; it now comes to its evaluation.

Nothing is to be changed in a mapping, a release or an installation. A run that `v0.1.0` completed is completed the same.

## Fixed: an unattended run that acquires two or more operation sources (#5)

Runner acquires each operation source in a Gateway session of its own: it names the session, takes the answer only as the session's first call, and asks Gateway to seal the session after. Its verifier took acquisitions of one session only. So it refused what Runner itself had acquired, on the legacy path and on the durable one, and the run was refused with no decision requested.

The verifier now takes the acquisitions of an input in either of two forms:

- they share a session, as Desk's preparation leaves them;
- each is alone in a session of its own and is that session's first call, as Runner leaves them.

An input in neither form is refused as before: two acquisitions that share a session beside one that does not, or an acquisition in a session of its own that is not its first call. One receipt still cannot stand in for two sources.

**What this gives up, and what it does not.** An input whose acquisitions are each the first call of a session of their own was refused before and is taken now, whoever submits it. `docs/MAPPING-V2.md` said, and says, that this verification is of receipts: it does not say a session is sealed or complete, nor that a caller did not choose among several answers. A caller who asked twice could choose in one session as in two. What an acquisition must still be is what it was: signed by the pinned key, of the pinned source, adapter and endpoint, committed to the exact arguments, of an admitted class, and fresh.

Citations of equal call index are recorded in the mapping's order of sources.

## What a release carries

Four archives, for Linux and macOS on `amd64` and `arm64`. Each holds `jpack-runner`, `jpack-source-worker`, `jpack-google-relay`, `openapi.json` and the licences. Windows is not released: it compiles, and nothing tests it.

To verify a download:

```sh
sha256sum --check --ignore-missing checksums.txt
gh attestation verify <archive> \
  --repo Judgment-Pack/judgment-pack-runner \
  --signer-workflow Judgment-Pack/judgment-pack-runner/.github/workflows/release.yml \
  --source-ref refs/tags/v0.1.1
```

On macOS use `shasum -a 256 --check --ignore-missing checksums.txt`. The releasing guide, linked below, has the form of the second command that holds a download to the commit as well.

## What this release does not establish

- That the fix holds against a real Gateway with two operations. The tests of two and three sources answer from a stand-in for Gateway, which signs as Gateway does; the test that uses the real Gateway and adapter has one operation, as before.
- The `darwin/amd64` archive is built and read, and run by nothing. `jpack-google-relay` is started by no release check.
- The archive checks start no job: a released program needs Runtime and a boot line to start one. CI's tests start jobs from source, within the test's own process. Nothing here tests the exchange of the boot line with Desk.

[docs/releasing.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.1.1/docs/releasing.md) says how a release is made and what each check does not establish.
