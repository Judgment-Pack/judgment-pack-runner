# v0.33.0

Runner v0.33.0 lets several Runners share one PostgreSQL store (#245, first step; #281, #283),
adds job schedules written as cron expressions within operator bounds and shared-interval
triggers that an external scheduler ticks through `POST /v1/ticks` (#246, #284), and makes the
trigger, pending-occurrence and run-queue limits service settings (#285, #288, #291). On the
PostgreSQL kind the Runner now serves the trigger, delivery, occurrence, retry, profile, journal
and run-chain routes held to their scope (#278, #290).

A Runner started as before, with the sqlite kind and no `schedules` or `limits` member, keeps
its limits (128 triggers, 100 pending occurrences, 100 runs queued or running) and its store's
schema until it writes the first cron or shared-interval trigger. The Spec's maturity remains
`draft`. This release claims no Extended Runner support.

A pre-release batch fixed the findings of the release review (this release's fix pull request):
a lock wait no longer stops a Runner's automation, a preparation no longer returns with its
claim held, and the operator documentation now covers the migration lists, a shared tick that
fails part-way, and the scope-wide routes.

## Compatibility

| With | What holds |
|---|---|
| Earlier Runner state directories (sqlite kind) | Open with no migration. A store keeps its schema byte for byte until the first trigger with a `cron` or `tick` schedule is written, which raises it to schema `"7"`. Every earlier Runner refuses a store at schema `"7"`. |
| A PostgreSQL store migrated by v0.32.0 | Must be migrated with this release's `jpack-runner store migrate` before a v0.33.0 Runner starts on it: it applies `0003` to `0006`. v0.32.0 refuses the migrated store. One-way: there is no migration back. |
| Service configuration files without `schedules` or `limits` | Run with the defaults: no shared interval, cron bounds of 60 s to 366 days, and the limits of v0.32.0. |
| Several Runners on one PostgreSQL store | Supported in this release, under the rules of [the postgresql store kind](../postgresql-store.md#several-runners-on-one-store): one release, the same `schedules` and `limits`, clocks within 1 s of each other. The sqlite kind keeps one Runner per state directory. |
| PostgreSQL | 16 is the version tested: CI runs the kind's tests against a `postgres:16` service container. |
| Judgment Pack Runtime | The tested Runtime moved to v0.46.0 (`d780245`). The other Runtime pins did not move; the Verified-with table lists them. |
| Judgment Pack Gateway | The durable Gateway contract the tests run against moved to Gateway v0.28.0 (`c5b12d2`). This release states nothing further about a Gateway. |
| Desk | Not pinned by this release; Desk adopts it in its own lane. |

## Behaviour changes

- A cloud binding another trigger already holds, named on `POST /v1/jobs`, answers `422
  cloud_binding_used`; before, the store's raw error (#290).
- A job upgrade whose trigger's cron or shared-interval schedule is outside the settings in
  force answers the schedule's `422` (`unknown_shared_interval`, `invalid_cron`,
  `cron_never_matches`, `cron_interval_too_short`, `cron_interval_too_long`), not `409` (#284).
- A request that changes a trigger while another writer, a request or another Runner's tick,
  writes it answers `409 trigger_changed`: read the trigger again and send the request again
  (#281).
- On the PostgreSQL kind, a retry on a host that does not hold every attempt directory of the
  run answers `409 run_not_retryable` (#278).
- On the PostgreSQL kind, the trigger, delivery, occurrence, retry, profile, journal and
  run-chain routes are served held to their scope; they answered `501
  store_route_unsupported` before (#278, #290).
- A refused job creation is journaled under no scope and is hidden from reads held to a scope
  (#278).
- A refusal at a limit names the configured value, not a fixed number (#288).
- A Runner on either kind takes a write refused at the PostgreSQL lock bound, in a tick of its
  own clock, a claim or dispatch of an occurrence, or a preparation, for a busy store and stays
  healthy; it tries again at a later tick. Before, its automation stopped and it answered `503
  dispatcher_stopped` until restarted. A shared tick still answers its caller with the error.

## What an operator must do

- **Nothing, to keep running as before on the sqlite kind.** Stop Desk and Runner and back up
  the Jobs workspace before the upgrade, as
  [State and backups](../../README.md#state-and-backups) describes.
- **To upgrade a PostgreSQL store:**
  1. Stop every Runner of the store.
  2. Run v0.33.0's `jpack-runner store migrate --connection <absolute path>` with the same
     logins as the first time. It applies `0003` to `0006` and prints
     `{"applied":["0003","0004","0005","0006"]}`.
  3. Start v0.33.0 Runners only, each with identical `schedules` and `limits` members, on
     hosts whose clocks are within 1 s of each other.
- **Know that the upgrade is one-way.** v0.32.0 refuses the migrated store; on the sqlite kind
  the first cron or tick trigger raises the store to schema `"7"`, which every earlier Runner
  refuses.
- **To tick shared intervals,** name them in `schedules.sharedIntervals` and run one external
  scheduler job per interval that calls `POST /v1/ticks` with the control API's credential and
  no scope identifier. Name `at` on every call, and call again with the same `at` after an
  error.
- **In front of a scope-bound caller,** a gateway or proxy must not forward `POST /v1/ticks`,
  nor `GET /v1/status` with `triggersOutsideSettings`: both span every scope
  ([security](../../SECURITY.md#security-boundary)).
- **Read the start's report.** At each start a Runner journals one `trigger.outside-settings`
  entry for each enabled trigger bound to a shared interval its configuration does not name, or
  whose cron expression is outside its bounds, and lists them in `GET /v1/status`. It changes
  none of them.

## Settings

| Member | Range | Default |
|---|---|---|
| `schedules.sharedIntervals` | at most 16 names, each minutes (`m`) or hours (`h`), or `1d`, from one minute to one day, dividing a day evenly | none |
| `schedules.minimumSeconds` | 60 to 31,622,400 | 60 (1 minute) |
| `schedules.maximumSeconds` | 60 to 31,622,400, not below the minimum | 31,622,400 (366 days) |
| `limits.triggers` | 1 to 1000 | 128 |
| `limits.pendingOccurrences` | 1 to 2000 | 100 |
| `limits.runQueue` | 1 to 2000 | 100 |

## New

- **`POST /v1/ticks`** `{"interval": ..., "at"?: ...}` answers `{"interval", "at",
  "occurrences"}`: it ticks the enabled shared-interval triggers of every scope bound to the
  interval, each due time once, whichever Runner of the store is called. Refusals: `422
  unknown_shared_interval`, `422 invalid_tick`, `400 invalid_scope`, `503 runner_unavailable`
  (#284, #288). The triggers are ticked one at a time; the call stops at the first whose tick
  fails and answers that error, and a call again with the same `at` ticks the rest.
- **Schedule kinds `cron` and `tick`.** A five-field cron expression in an IANA zone, held to
  the operator's bounds (`422 invalid_cron`, `cron_never_matches`, `cron_interval_too_short`,
  `cron_interval_too_long`); a shared interval, with or without a cron expression (#284).
- **Several Runners on one PostgreSQL store.** A lease per occurrence; one due time makes one
  occurrence; each queued run and each occurrence is worked by one Runner at a time; a Runner
  that stops has its work interrupted one lease later and not repeated (#281, #283, #290).
- **Status members** `schedules`, `limits` and `triggersOutsideSettings`; **capabilities**
  `cron-schedules` and `shared-interval-ticks`; **journal kind** `trigger.outside-settings`.
  A shared tick's occurrence entries name the caller (#284, #288, #291).

## Limits

| What | Value |
|---|---|
| Claim lease, by the database's clock | 60 s |
| Lease renewal | every 15 s |
| `lock_timeout` | 5 s |
| Own clock's grace before a due time counts as missed | 30 s |
| How far ahead of the Runner's clock a tick may be named | 30 s |
| How far behind the Runner's clock a tick may be named | one interval |
| Occurrences dispatched per pass of the automation | 10 |

## Fixed in the pre-release batch

- **A lock wait stopped every Runner's automation.** A schedule or file tick, the claim of a
  ready occurrence and a preparation's claim or write that waited out the lock bound marked the
  Runner unhealthy. They now make nothing and are tried at a later tick, as the dispatcher's
  writes already were (`tickLost`, `occurrenceLost`).
- **A preparation returned with its claim held on an error.** It now fails an occurrence whose
  own record cannot be prepared, and otherwise releases the claim first, a durable step with
  the occurrence as the store holds it, so that a committed source task is kept.
- **Documentation:** the migration lists name `0001` to `0006`; why every start journals each
  trigger outside the settings again; what a shared tick that fails part-way answers and what
  to do; that `POST /v1/ticks` and `triggersOutsideSettings` span every scope.

## What this release does not establish

- **A start that meets an unreadable trigger or job record is refused,** as before: the start's
  check of the triggers outside the settings stops at it. Reporting the record and going on is
  not built.
- **Routes not served on the PostgreSQL kind.** A run's diagnostics and verification, the
  briefs of a job or a run, the execution binding, `GET /v1/background-connections` and the
  input preparation routes still answer `501 store_route_unsupported`.
- **No process group on stop (#265).**
- **Tests not built (#267).**
- **Removal of one scope's rows is not built** (design D10). `jpack-runner store` takes
  `migrate` and nothing else.
- **Restoring a store from a backup is not tested.**
- **Replacing Runners one at a time is not supported.** A store holds one release: stop every
  Runner to upgrade.
