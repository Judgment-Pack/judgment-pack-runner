# v0.29.0

Runner v0.29.0 carries five changes since v0.28.0:

- runs say whose reviewed set their reviewed claim is about, and a release check can ask
  for the Runtime's `requireComparableFacts` (#210, #223);
- the token event route answers 429 at a full queue and leaves the event ID unused (#211,
  #224);
- a release check can hold the pack to a reviewed-set lock supplied with it, which the
  pinned Runtime's `packs covers` checks (#210, #225);
- a release whose sample derives no fact gets a review warning (#212, #228);
- six findings of the pre-release review are fixed (#230).

The new release-check options and boot members are off unless asked for. The event route's
answer at a full queue changes, and so does what an earlier `verify-run` accepts. Some
senders, hosts and verifiers that worked with v0.28.0 are answered differently by v0.29.0,
as set out below. The companion pins do not move. The Spec's maturity remains `draft`.
This release claims no Extended Runner support.

## Breaking changes

1. **An event delivery at a full queue is refused, not recorded `skipped` (#211, #224).**
   While 100 occurrences are pending in the store (`accepted`, `preparing` or `waiting`,
   of any trigger), `POST /v1/triggers/{trigger}/events` answers 429 `queue_full`, with
   `retryable: true`, and admits nothing. v0.28.0 acknowledged such a delivery with an
   occurrence recorded `skipped`, reason `queue-full`.
   - The event ID stays unused. The same bytes sent again are admitted once the queue has
     room, while `occurredAt` is no more than five minutes old. After that they are
     refused with 422 `event_expired`, as any delivery with an old timestamp is.
   - An ID that v0.28.0 recorded as `skipped` with reason `queue-full` still answers with
     that recorded occurrence.
   - The answer carries no `Retry-After` header.
   - The record route (`POST /v1/triggers/{trigger}/deliveries`) already answered 429 at a
     full queue and is unchanged. A schedule, a file change or a cloud signal has no
     sender to answer, and is still recorded `skipped`, reason `queue-full`.
2. **A `verify-run` before v0.29.0 refuses the export of a run whose release was checked
   against a supplied reviewed set (#225).** The export's release carries
   `suppliedReviewedSet`, and the v0.28.0 `verify-run` fails with
   `json: unknown field "suppliedReviewedSet"`; export versions 3, 4 and 5 were tried.
   Other exports verify with both, those of releases checked with `requireComparableFacts`
   or carrying the new warning among them.
3. **The run routes read the run's release (#223, #225).** `GET /v1/runs/{run}` and
   `POST /v1/jobs/{job}/runs` now read the release of a run whose result or audit record
   says `reviewed: true`. Where v0.28.0 served the run, they answer 500 `store_error` when
   that release cannot be read, or when the supplied lock it keeps is no longer the bytes
   its digest names. A replay of a completed run through `POST /v1/jobs/{job}/runs` is
   answered the same way.
4. **The two new boot members are `true` or `false` (#223, #225).**
   `requireComparableFacts` and `requireSuppliedReviewedSet` refuse the boot when written
   `null`, as a string, or under a second spelling of the name. v0.28.0 ignores both
   members, starts with any of these, and applies no gate.
5. **`requireTestedReleases` is `true` or `false` (#230).** The boot is refused when the
   member is written `null`, as a string, or under a second spelling of the name. v0.28.0
   started with any of these: written `null` the gate was off, and of two spellings the
   later one won. A boot line that writes it `true` or `false` once is read as before.

## Additive changes

- `POST /v1/previews` takes `requireComparableFacts` (#223) and `reviewedSet` (#225). A
  release check without them is checked as before.
- `Release` gains `suppliedReviewedSet` (`id`, `lock`, `lockDigest`) for a release checked
  against a supplied lock. A release checked with `requireComparableFacts` has the
  configVersion 5 `config`. A release checked with neither has the members it had.
- `GET /v1/runs/{run}` and `POST /v1/jobs/{job}/runs` gain `reviewedSetOrigin` (`release`
  or `supplied`) and `suppliedLockDigest`. They are read off the run and its release each
  time the run is served, so runs completed before the upgrade carry them too. Run lists,
  briefs and verification exports do not carry them.
- New codes on a release check: 422 `comparable_facts_unsupported`, `invalid_reviewed_set`,
  `pack_not_in_reviewed_set` and `reviewed_set_unsupported`. New codes at job creation and
  upgrade: 409 `release_comparable_facts_required` and `release_reviewed_set_required`.
  The event route now answers the existing 429 `queue_full`.
- The boot line takes `requireComparableFacts` and `requireSuppliedReviewedSet`.
- Mapping-v2 review warnings gain the no-fact warning (#228).
- `openapi.json` names the new members, and now documents `Release.config` and
  `Release.lock`, which every release already carried.
- `GET /v1/status` gains no capability string for any of this (#227). The store schema is
  unchanged and there is no migration.

## What an operator must do

- **Treat 429 `queue_full` from the event route as retryable.** Send the same bytes again
  within five minutes of `occurredAt`. Check that a relay in front of the route, Desk's
  `POST /api/job-events/{trigger}` among them, passes the 429 on to its sender.
  This release did not check Desk's relay; that is for Desk's lane when it adopts this
  Runner.
- **Write `requireTestedReleases` as `true` or `false`, once** (breaking change 5).
- **Pin Runtime 0.41.0 or later for `reviewedSet`.** An earlier Runtime has no
  `packs covers`, and every check with `reviewedSet` is refused as 422
  `reviewed_set_unsupported` (Runtime 0.40.0 was tried). `requireComparableFacts` needs
  Runtime 0.25.0 or later.
- **Pin this Runner where a host relies on a boot member.** A Runner before this one
  ignores `requireComparableFacts` and `requireSuppliedReviewedSet`, and applies no gate.
  A host that sets `requireSuppliedReviewedSet` also pins Runtime 0.41.0 or later.
- **Keep this `verify-run` for exports of releases checked against a supplied lock**
  (breaking change 2).
- **Do not read `"supplied"` as a control.** The lock is the caller's: `"supplied"` and
  `requireSuppliedReviewedSet` show only that some lock naming exactly these pack bytes
  was supplied with the release check. A consumer that needs a particular reviewed set
  compares `suppliedLockDigest` with the digest of a lock it obtained from a source it
  trusts.
- **Accept the new members in strict clients.** A client that refuses unknown members of
  a run must accept `reviewedSetOrigin` and `suppliedLockDigest`, which every completed
  reviewed run now carries, those made before the upgrade included.
- **Do not downgrade an installation that holds releases checked against a supplied
  lock.** v0.28.0 drops `suppliedReviewedSet` when it reads such a release: its attempts
  are no longer checked against the lock, its runs say no origin, and its exports carry a
  different `releaseDigest`. A release checked with `requireComparableFacts` keeps its
  stored configVersion 5 configuration. v0.28.0 ignores both boot members.
- The usual care applies before any upgrade: stop Desk and Runner and back up the Jobs
  workspace, including SQLite/WAL, as
  [State and backups](../../README.md#state-and-backups) describes. The store schema is
  unchanged and there is no migration.

## Whose reviewed set a run's claim is about (#210, #223)

A release is a frozen pack, not a project. Runner generates the configuration its Runtime
reads, and the pinned Runtime's `packs lock` writes the release's own reviewed-set lock
over that configuration and the pack. Every evaluation of the release is given those and
nothing else, so a run's `reviewed: true` shows only that the pack the run applied is the
pack the release froze. It shows neither that a project reviewed the pack nor that a
project's lock names it. The run routes now say so, with `reviewedSetOrigin: "release"`.
The README section
[What a run's reviewed claim means](../../README.md#what-a-runs-reviewed-claim-means)
gives the account.

### Comparable facts

With `"requireComparableFacts": true` in `POST /v1/previews`, Runner gives the release the
configVersion 5 configuration that sets `requireComparableFacts`, in place of the
configVersion 3 one ([Comparable facts](../../README.md#comparable-facts) shows it). Its
Runtime then refuses every evaluation of the release, the sample's rehearsal included, in
which a fact some comparison of the pack reads is present and of a JSON type that
comparison can never match (`JPS-FACTS-COMPARABLE-REQUIRED`). Such a sample fails the
check as `preview_failed`, and such a run fails. Saved tests run under a configuration of
their own, which does not set it.

Runner first asks the pinned Runtime, with `packs schema --format json`, whether it lists
`"5"` among its `supportedConfigVersions`. An answer that does not, or that cannot be read,
refuses the check as 422 `comparable_facts_unsupported`, and no release is saved. Under
manual admission the option is refused as 409 `manual_profile_unsupported`.

With `"requireComparableFacts": true` on the boot line, creating a job from, or upgrading a
job to, a release whose configuration is not that one byte for byte returns 409
`release_comparable_facts_required`. As with `requireTestedReleases`, only the creation or
upgrade is refused: repeating the creation of a job made before returns that job, and its
runs keep running.

A `requireComparableFacts` written `null` in a release check is refused as 400
`invalid_request`, as a `reviewedSet` written `null` is (#230).

An invocation of `packs schema` that does not exit is still answered as 422
`comparable_facts_unsupported` (#229).

## The event route at a full queue (#211, #224)

Whether 100 occurrences are pending is decided in the admission transaction. At that limit
the token event route rolls the transaction back and answers 429 `queue_full`, as the
record route has since #70 (breaking change 1). The refusal is journaled as
`admission.refused`, once a minute for alike refusals, and no occurrence is recorded. The
README section [Event delivery](../../README.md#event-delivery) and `openapi.json`
(`deliverEvent`) state the rule.

## Supplied reviewed sets (#210, #225)

`POST /v1/previews` can take, beside the pack, `"reviewedSet": {"lock": ..., "id": ...}`:

- `lock`: the exact bytes of a lock the Runtime's `packs lock` wrote, from 1 byte to 1 MiB;
- `id`: the decision id the pack is locked under in it, at most 128 characters, in the
  form a Runtime configuration gives a decision id.

A lock or id outside those bounds is refused as 422 `invalid_reviewed_set` before anything
is written. A `reviewedSet` written `null` is refused as 400 `invalid_request`.

Runner writes the lock, readable by its owner alone, beside the pack in the release's
directory. Before the pack is validated, it asks the pinned Runtime, with no shell and
without `--config`,
`packs covers --lock reviewed-set.lock.json --id ID --pack pack.json --format json`
(Runtime ADR-0072). Runner does not read the lock: the Runtime is the one reader of its
format. The release is checked only when the Runtime answers that the lock covers the
pack's exact bytes under the id. Any other answer refuses the check, and no release is
saved:

- 422 `pack_not_in_reviewed_set`, naming the Runtime's findings, such as
  `lock-entry-missing` or `document-drift`;
- 422 `invalid_reviewed_set`, naming the Runtime's code, one that begins `JPS-LOCK-` or
  `JPS-RESOURCE-LOCK-`;
- 500 `store_error` for any other code the Runtime refuses with, such as one about the
  pack file Runner wrote, and for an invocation that did not exit: a Runtime that could
  not start, was killed, or was still running at the deadline (#230);
- 422 `reviewed_set_unsupported` for anything else, among it the answer of a Runtime
  before 0.41.0, which has no `packs covers`.

A refusal carries neither the lock's bytes nor the Runtime's messages.

The release keeps the lock as `suppliedReviewedSet`, and its own configuration and lock
are unchanged. `packs covers` is not asked again at each attempt. Each attempt checks by
digest that the release still holds that pack, that lock and the Runtime it pinned, and
an attempt whose kept lock is no longer its digest's fails without being evaluated. The
verification export of a run of such a release is refused with 500 `store_error`, and
`verify-run` fails an export whose `suppliedReviewedSet.lock` is not the bytes its
`lockDigest` names (#230). `verify-run` does not ask a Runtime about the lock again. Under
manual admission the option is refused as 409 `manual_profile_unsupported`.

With `"requireSuppliedReviewedSet": true` on the boot line, creating a job from, or
upgrading a job to, a release not checked against a supplied lock, or one whose kept lock
is no longer its digest's, returns 409 `release_reviewed_set_required`. Only the creation
or upgrade is refused, as with `requireComparableFacts`.

**The lock is the caller's.** A lock is a document anyone can write. The check says that
this lock pins these bytes under this id. It does not say that a project's configuration
declares the pack, or that the lock is the one a given project holds. `"supplied"` and
`requireSuppliedReviewedSet` are no control against whoever may call `POST /v1/previews`.
The README section [Supplied reviewed sets](../../README.md#supplied-reviewed-sets) gives
the account, and [the design note](../design/supplied-reviewed-sets.md) the decisions.

## A sample that derives no fact (#212, #228)

A mapping-v2 release whose sample's derivation has fact targets and yields none of them
gets one more review warning, after the others:

> The sample derived no fact: the release's sample shows nothing of how the mapping turns
> a record into facts.

It is a warning, not a refusal. A mapping with only evidence targets does not get it. The
warning is part of the saved release and of its digest, for releases checked from now on.
A release saved before is not recomputed and keeps the warnings it has.
[MAPPING-V2](../MAPPING-V2.md) states the rule.

## What this release does not establish

- **No accepted locks and no capability string (#227).** An installation cannot name the
  lock digests it accepts, and a host cannot ask this Runner whether it has the new
  members; it pins the version.
- **A refused check's directory is not removed (#226).**
- **The journal does not say how a release was checked.** The `release.previewed` entry
  records neither a supplied reviewed set nor `requireComparableFacts`.

## Known limitations

- **Hung mount (#209).** Every `GET /v1/status` stats the bound input root, so a mount
  that does not answer can hold the status reply.
- **`adapter-http` query at job creation (#208).** A release saved with a query outside
  dialect §4.1 can still become a job, and every run of that job then fails.
- **No `Retry-After`.** A 429 `queue_full` names no time to wait.
- **A refused retry is checked in full.** Each retry of an event at a full queue checks
  its input again, where v0.28.0 answered it from the occurrence it recorded.
- **Path members not checked.** The boot line's `signingKey` and `executorOwnership.root`
  are not held to the path domain. The whole boot line must still be valid UTF-8.
- Raw-byte workspace and input roots are not supported, and there is no byte-exact
  relocation route (#202).
- **`packs schema` that does not exit (#229).** It is reported as a Runtime too old for
  comparable facts.

`serve`'s write timeout is now 245 seconds, from 135, to leave room for every Runtime
invocation a release check can make (#230).
