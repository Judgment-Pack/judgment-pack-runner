`verify-run` now says what it cannot vouch for: which of a run's inputs nothing but the export vouches for, and which rule parameters no signed request commits. With `--require-sourced` it refuses such a run. A run also keeps its audit record's exact bytes, and a new export version carries them, so the record can be compared with the digest a gateway receipt names. Nothing is refused that `v0.3.0` accepted, unless it is asked for.

## What an operator must do

- **Nothing, to keep things as they are.** The verification export is version 2 unless version 3 is asked for, and version 2 is byte for byte the export `v0.3.0` made. `verify-run` accepts exports written by `v0.3.0`, and without `--require-sourced` it refuses nothing it accepted before. Profiles, mappings and releases encode as before.
- **A program that reads `verify-run`'s report must allow for new output.** Its JSON gains `exportVersion`, `exactBytes` and `targetsByClass`, and, when they apply, `unsignedParameters` and `recordDigest`. The line on standard error gains sentences. A reader that compares either exactly must be updated.
- **To refuse inputs nothing vouches for:** add `--require-sourced`. A refused run exits 1 with the status `inputs-asserted` or `parameters-unsigned`.
- **To compare a record with a gateway receipt:**
  - ask for `GET /v1/runs/{run}/verification?version=3`;
  - run `verify-run` on that export;
  - compare its `recordDigest` with the receipt's `decision.recordDigest`. `verify-run` reads no receipt, so the comparison is yours.
- **Desk `v0.4.1` cannot fetch version 3.**
  - It forwards to Runner only the query parameters it names, and `version` is not one of them.
  - It reads at most 16 MiB of a Runner response, and a version-3 export may reach about 18.7 MiB.
  - Until Desk changes, read version 3 from Runner's own API.
  - `GET /v1/runs/{run}` now carries the audit record twice, parsed and in base64. A run whose record is several MiB therefore reaches Desk's limit sooner.

## Which inputs were asserted (#27, closes #24)

`verify-run` recomputes every input the same way, but what that establishes depends on where the input came from. Its report now says so.

- **`targetsByClass` counts the run's fact and evidence targets** by the class of the source each is mapped from: `record`, `generated` or `asserted`. Every target is counted, including one without a value and one whose source was skipped.
- **An `asserted` target** was typed into the case or read from a local file, and nothing but the export vouches for it. An export whose asserted inputs were rewritten after the run, with its preparation, result and audit record recomputed to match, verifies as the original did, with or without `--runtime`. The line on standard error now says when inputs are the operator's own.
- **`--require-sourced` refuses a run with an asserted target,** whether or not the run has a value for it, as `inputs-asserted`. The refusal comes before any re-execution, so with `--runtime` the executable is not run.
- **It lets through** a `generated` target, whose receipt says what the source answered and not that the answer is true, and a target of a skipped source, which has no value and no receipt.

## Which rule parameters no signed request commits (#31, closes #29)

Not every parameter a rule reads is signed. A parameter is committed when the source's own signed request carries it unambiguously, or when a calculator's signed answer echoes it. A request carries a parameter unambiguously as a whole value, or in `$text` that names no other parameter. A parameter that neither commits can be changed in an export, for example to turn evidence from `present` to `unknown`, and the export still verifies.

- **`unsignedParameters` names such parameters.** For each acquired source whose rule reads one, it gives the source, each parameter's `name` and `kind`, and how many targets the source maps. The kinds are `case`, `local-file`, `upstream`, `ambiguous-text`, `runAt` and `upstream-runAt`. [MAPPING-V2.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.4.0/docs/MAPPING-V2.md) defines each kind.
- **Another source's receipt does not commit a parameter for this one.** A value derived from an unsigned parameter carries that taint to a later source.
- **A rule reads only what its conditions name.** These are `equalsParam`'s `param`, and `freshWithin`'s `asOf` and `maxAge`, at any depth. A parameter it only declares is not read.
- **`verify-run` works the member out from the frozen mapping and the run's outcomes.** The stored lineage is unchanged.
- **`--require-sourced` refuses a target derived from a parameter of kind `case`, `local-file`, `upstream` or `ambiguous-text`,** as `parameters-unsigned`. When a run also has an asserted target, the status is `inputs-asserted`, and the report shows both.
- **`runAt` and `upstream-runAt` are reported but not refused,** so that freshness checks that use the run's time are not refused. The report and the line say that such a verdict rests on the export's own verification time.

## The audit record's exact bytes (#32, closes #28)

A gateway action receipt names the record it relied on by `decision.recordDigest`: the SHA-256 of the bytes the Runtime wrote. Runner kept the record parsed and encoded it again, with `&`, `<` and `>` escaped. That is the same JSON value, but in other bytes, with another digest. With Runtime `v0.24.0` this happens, for example, when the pack's identifier contains an `&`.

- **A run now keeps the record's line exactly,** as `run.auditBytes`, in standard base64. `GET /v1/runs/{run}` shows it; run lists and briefs leave it out. A run recorded before this release has none, nor does a run without an audit record.
- **The verification export has a version 3,** served for `?version=3`, which carries those bytes beside the parsed `run.audit`.
  - Without a version, or with `?version=2`, the export is version 2, unchanged.
  - A run that holds no bytes is exported as version 2 even when version 3 is asked for.
  - Any other version, a repeated `version`, or a malformed query is refused with `invalid_version`.
- **Version 3 is held to version 2's 8 MiB, not counting the member that carries the bytes.** The bytes themselves are held to 8 MiB, so a version-3 export may reach about 18.7 MiB.
- **`verify-run` accepts both versions.** Of a version-3 export, it also checks three things:
  - the bytes are one line;
  - they parse as strictly as the export does;
  - they are the same JSON value as `run.audit`.

  It reports their SHA-256 as `recordDigest`. Of a version-2 export, it reports `"exactBytes":"not-in-export"` and says that exact-byte checks were not possible.

## "Immutable", defined (#26, closes #25)

The README now says once what "immutable" means for a release and a recorded operation request: Runner offers no operation that changes one. It is not protection against whoever can change the store.

## What a release carries

Four archives, for Linux and macOS on `amd64` and `arm64`. Each holds `jpack-runner`, `jpack-source-worker`, `jpack-google-relay`, `openapi.json` and the licences. Windows is not released: it compiles, and nothing tests it.

To verify a download:

```sh
sha256sum --check --ignore-missing checksums.txt
gh attestation verify <archive> \
  --repo Judgment-Pack/judgment-pack-runner \
  --signer-workflow Judgment-Pack/judgment-pack-runner/.github/workflows/release.yml \
  --source-ref refs/tags/v0.4.0
```

On macOS use `shasum -a 256 --check --ignore-missing checksums.txt`. The releasing guide, linked below, has the form of the second command that holds a download to the commit as well.

## What this release does not establish

- **That an input is true.** The report says what nothing but the export vouches for. A signed response says what the source answered, not that the answer is true, and `--require-sourced` lets a `generated` target through.
- **That a parameter's request chose the right record.** A committed parameter fails verification when it is changed, but the record it chose remains the caller's assertion.
- **That version 3's bytes are the ones the Runtime wrote for this run.**
  - They are consistent with the record the export carries, and their digest is the one a gateway receipt would name for them.
  - Only a comparison with a digest held independently of the export, such as a receipt's, shows that they are original.
  - Nothing binds the record to the run beyond the existing checks. Another run of the same release with the same inputs could supply its own record and bytes.
  - Bytes re-encoded without changing their value also verify, with another digest.
- **That a store's contents are tamper-evident** to whoever can change the store. Nothing in this release chains, signs or witnesses a record ([runtime ADR-0047](https://github.com/Judgment-Pack/judgment-pack-runtime/blob/v0.25.0/docs/adr/0047-make-a-decision-record-defensible.md); #30).
- **That it works with Runtime `v0.25.0`.** CI tests `v0.24.0`.
- **That the release runs on every platform.** The `darwin/amd64` archive is built and read, but nothing runs it. No release check starts `jpack-google-relay`.
- **That a released program starts a job.**
  - The archive checks start no job, since a released program needs Runtime and a boot line to start one.
  - CI's tests start jobs from source, within the test's own process.
  - Nothing here tests the exchange of the boot line with Desk.

[docs/releasing.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.4.0/docs/releasing.md) says how a release is made and what each check does not establish.
