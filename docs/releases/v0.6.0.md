**A store this release opens is migrated to schema `"2"`, in one transaction, and Runner `v0.5.0` and earlier then refuse it**, with "runner store belongs to another owner, workspace or schema". Going back to an earlier Runner needs a copy of the store from before the update: back the store up before updating, and nothing else is needed. The migration begins the store's journal of job activity, and nothing from before it is back-filled.

Beyond that, Runner now records each change of state it makes in that journal, and serves it in order. It exports a run without lineage when the run's job has no mapping or a v1 mapping, and it serves a finished run's Runtime diagnostics under a bound. Apart from the store's schema, nothing `v0.5.0` accepted is refused.

## What an operator must do

- **Back up the store before updating.** Stop Desk and the runner, then copy the entire Jobs workspace directory, as [State and backups](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.6.0/README.md#state-and-backups) says. The first start of this release migrates the store. If the migration fails, it leaves the store as it was. Once it succeeds, the only way back to `v0.5.0` is to restore that copy, which loses whatever happened since.
- **Nothing else, to keep things as they are.**
  - A mapping-v2 run's verification export is byte for byte what `v0.5.0` made, at every version, and `verify-run` reports it as before.
  - Without `signingKey` in the boot line, nothing is signed, as before.
- **A program that reads run records must allow two new members:**
  - `interruptedAt`, on a run Runner saw stop at an orderly stop;
  - `reason`, `"queue-expired"`, on an automatic run whose queue time ran out.

  Both appear on `GET /v1/runs/{run}`, the submit answer and run lists, and in no verification export.
- **A program that reads `verify-run`'s report must allow for an export without lineage.** Its report has `"inputs":"not-mapped"` and no `targetsByClass`. `--require-sourced` refuses such a run, with the status `inputs-not-mapped`.
- **A program that compares the 422 `not_verified_mapping` message exactly must be updated.** The message now says which versions an export without lineage can be.
- **`GET /v1/status`** lists two new capabilities, `activity-journal` and `run-diagnostics`.
- **Desk cannot yet reach any of this.** See [Desk](#desk).

## A journal of job activity (#48, closes #41)

Runner kept each record's latest state, not its history. It now keeps a journal beside those records. The design is recorded in [docs/design/activity-journal.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.6.0/docs/design/activity-journal.md), proposed in #45 and accepted in #46.

- **One entry per change of state, in the same transaction.** A writer that changes a record reads the record's stored state inside its transaction. It writes an entry exactly when the state it writes differs. A request that changes nothing writes no entry.
  - The writes that were single statements are now transactions: a run's start and queue expiry, every occurrence change, a preparation's progress, the release insert, and the restart's marks.
  - There are 26 kinds:
    - triggers: configured, paused, resumed, key rotated;
    - occurrences: received, skipped, preparing, ready, submitted, failed, expired, needs attention, cancelled, reconciled;
    - runs: queued, started, expired, completed, failed, interrupted;
    - `release.previewed`, `job.created`, `admission.refused`;
    - `journal.began`, `runner.started`, `runner.stopped`.
- **Who.** Each entry names what Runner can know initiated it, and never a person:
  - the installation, by the boot line's owner;
  - a trigger, at its revision;
  - a trigger's credential, named by the revision at which its key was issued, never the token or its digest;
  - a cloud connection;
  - Runner itself.
- **Configuration is named by revision only.** No entry copies a trigger's values, a key, an input or an address.
- **Refused admissions.** A request to start work is journaled as `admission.refused` when it was answered 400, 401, 409, 422 or 429 and names a job, trigger or release the store holds. The requests are submitting a run, delivering an event, and creating a job. Every cloud signal Runner discards is journaled too. An identical refusal within 60 seconds of one already written is not written again.
- **Restarts and interruptions.**
  - Each start writes `runner.started`, and each orderly stop writes `runner.stopped`.
  - A run Runner saw stop keeps `interruptedAt` beside `finishedAt`, and `finishedAt` keeps its meaning.
  - A run found running at a start has no `interruptedAt`. Its entry gives the window instead: from the run's `startedAt` to the start's own entry.
- **The schema.** The store's `schema` metadata goes from `"1"` to `"2"`, with an `events` table and a `key_revision` column on triggers. The first entry, `journal.began`, says when the journal began and how many jobs, triggers, occurrences and runs the store already held.
- **Routes.** `GET /v1/jobs/{job}/events?after=` and `GET /v1/events?after=&job=` serve the journal.
  - Pages hold 50 entries, oldest first, and `after` means later than. `next` never resets to 0, so a reader that has caught up asks again with it.
  - Every page carries `journalBegan`.
  - The routes are in `openapi.json`, and [MAPPING-V2](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.6.0/docs/MAPPING-V2.md#the-journal-of-job-activity) describes them. `internal/runner/testdata/journal-entries.json` holds one entry of every kind.

## Exports without lineage (#47, closes #44)

A run of a job with no input mapping, or with a v1 file mapping, has no lineage. Once completed, it still holds its audit record's exact bytes, its entry in the chain of runs and, under a signing key, its signature sidecar. Its export was refused with 422 until now.

- **Export.** Such a run is now exported at version 3, 4 or 5, by the same steps as any run. The export has one more member, `"inputs":"not-mapped"`, and no lineage.
- **The 422 that stays:** a run without the record's bytes, at any version, and any such run asked for version 2 or for no version.
- **`verify-run`** holds such an export to the record's bytes, the chain entry and the signature, exactly as any export. In place of lineage, it checks four things:
  - the release froze no mapping v2;
  - the run names the release and its mapping;
  - the audit record evaluated the run's retained facts and evidence;
  - the record names no citation.

  `--require-sourced` refuses such a run, as `inputs-not-mapped`.
- **A mapping-v2 run's export is unchanged,** byte for byte, and has no `inputs` member.

## A run's diagnostics, and an expired queue entry's reason (#49, closes #42)

- **`GET /v1/runs/{run}/diagnostics`** serves what the Runtime wrote when it evaluated the run, as `text/plain`: its standard error, or with `?stream=stdout` its standard output.
  - **Bound:** the first 65,536 bytes, cut before a character the bound would split. `X-Diagnostics-Bytes` gives the stream's whole size, and `X-Diagnostics-Truncated` says whether it was cut.
  - **Refusals:** a run still queued or running gets 409 `run_not_finished`. A run whose stream is not retained gets 404 `no_diagnostics`, with its state and only what the store records of it.
  - **Containment:** the stream is read through the attempts directory Runner holds. Runner serves only the file it looked at and then opened, checked on the opened descriptor to be that same regular file, private to the operator. Anything else is refused with 500 `diagnostics_refused`, and nothing of it is served.
  - A read writes no journal entry.
- **An expired queue entry's reason.** An automatic run whose queue time ran out keeps `"reason": "queue-expired"`, so a reader need not parse its `problem`. Its state stays `failed`. A run that expired before this release has no reason, and is not given one.
- **An interruption's time** was delivered by #48. #42 first proposed putting the restart's time in `interruptedAt`; that proposal is superseded. The restart's time stays in `finishedAt` and in the restart's own entry.

## What each part establishes and does not

- **The journal is the operator's own log.**
  - It is not chained and not signed. It is kept in the store the operator holds and can rewrite, and it is never pruned.
  - It binds nothing against the operator, and says nothing of who a person was.
  - Its times are Runner's clock, and its order is `sequence`.
  - A refusal's entry is best effort: if the store cannot write it, the refusal is answered as it was and has no entry. Identical refusals within a minute of an entry are not entries.
  - Nothing from before `journalBegan` has an entry.
- **An export without lineage establishes nothing about where the run's inputs came from.** They are the operator's own. What it establishes is what the record's bytes, the chain entry and the signature establish of any run. Against the operator, it establishes nothing without a checkpoint held by someone else.
- **Diagnostics are the Runtime's own words, kept in the operator's store.** They explain a run, and establish nothing about it.
- **What `v0.5.0` did not establish** still holds ([v0.5.0's notes](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.6.0/docs/releases/v0.5.0.md#what-this-release-does-not-establish)):
  - from the chain alone, or from a signature, nothing against the operator;
  - that an input is true;
  - that a released program starts a job with Desk.
- **What was not exercised.**
  - By hand, macOS was not run; CI runs the suite on macOS `arm64`. The `darwin/amd64` archive is built and read, but nothing runs it.
  - The durable Gateway path's journal entries, `occurrence.preparing` and `occurrence.ready` through a real Gateway and MCP adapter, are not asserted by the integration test. That test passed with real binaries, and the journal's own tests reach those transitions through a stand-in source worker.

[docs/releasing.md](https://github.com/Judgment-Pack/judgment-pack-runner/blob/v0.6.0/docs/releasing.md) says how a release is made and what each check does not establish.
