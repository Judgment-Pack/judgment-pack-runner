The third finding of the cross-vendor audit of the chain of runs (tracking #57) is fixed (#54). Runner now reads its signing key once, at start, and fixes that key's public key as the expected key for as long as it runs. It passes the expected key to each run's Runtime, and holds each completed run's signature to it. A seed replaced at its path after start can no longer sign runs unnoticed: Runtime 0.30.0 and later refuse to sign with it, and with any Runtime the run says that its signing failed.

## What an operator must do

- **Check that your signing key is a seed before updating.** Runner now reads the key that `signingKey` names when it starts. If the file is not the Runtime's seed form (64 hexadecimal characters with nothing else but surrounding whitespace), Runner refuses to start, as it does for a misplaced key. The refusal names neither the path nor anything the file holds. A key made by `jpack audit key generate` or the gateway's `keygen` passes.
- **Name the expected key on the boot line, if you can.** `signingPublicKey` (64 lowercase hex) names the public key the signing key must have, independently of its file; Desk can pass it from its list of public keys (Desk #345). Runner then refuses to start with any other key at the path. Without it, Runner expects whatever key it reads at start.
- **Use Runtime 0.30.0 or later to prevent a replaced key from signing, not only to detect it.** An earlier Runtime ignores `JPACK_SIGNING_PUBLIC_KEY` and signs with whatever seed is at the path; Runner then names the failure on the run.
- **A program that reads runs** sees one new member on a completed run of an installation with a key: `signing`, beside `auditSignatures`, in `GET /v1/runs/{run}` and in run lists.
- **Nothing else.** The store's schema, the chain of runs, the export versions, and `verify-run`'s report and exit codes are unchanged.

## A replaced signing key cannot sign completed runs unnoticed (#54)

- **The expected key is fixed at start.** Runner reads the seed at the checked path once, without following a link, through one handle on the file it checked, held to the same checks, and to at most the 4096 bytes the Runtime reads. It refuses to start if the file's identity, size, links, mode, owner, modification time or change time changed between the check and the end of the read (review of #62). It derives the public key and keeps nothing else. With the boot line's `signingPublicKey`, the derived key must be the one named, which is then the expectation (review of #62).
- **Every operational evaluation gets both inputs:** the path as `JPACK_SIGNING_KEY`, as before, and the expected key as `JPACK_SIGNING_PUBLIC_KEY`. Rehearsals get neither, as before.
- **Each completed run's signer is held to the expected key**, by the check `verify-run --public-key` makes, over the record's bytes and the sidecar the run keeps. A signed run carries `"signing":{"status":"signed","publicKey":"<expected key>"}`, so each run keeps the key it was signed under. Any other run carries `"signing":{"status":"failed","reason":"..."}`, with one of six fixed reasons (MAPPING-V2, "A run's signing"). Among them are a sidecar that names another key, a Runtime that signed nothing because the key at the path is not the expected key, and a sidecar that could not be read, which is never taken for no sidecar. The run still completes with its decision.
- **A sidecar that cannot be read no longer fails a run of an installation with a key:** it fails the run's signing. Without a key, it fails the run, as before.
- `verify-run --public-key <expected> --require-signed` refuses a run signed under another key, or not at all, as it did. An export does not carry `signing`: version 5 carries the sidecar itself.
- **Not in this release:** rotating the key (Desk #238), and Desk's Jobs record panel (Desk #345).
