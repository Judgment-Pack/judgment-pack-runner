Runner v0.18.0: an offline `verify-preparation` command replays a standalone fixture against its retained profiles, binding and historical instant in the dialect companion's §11 report form, with capability discovery; a new input profile is registered without restarting jobs; two conformance clarifications in the profile admission's comment.

## What an operator must do

- **Nothing for existing runs.** Exports, the journal, `verify-run`'s report, its exit codes and refusal flags are byte-identical to v0.17.0's for every existing run; all forty-one published vectors recompute byte for byte. Every live path (submission, preview, the loop, import, `verify-run`) keeps every outcome and message it had.
- **To verify an Exchange fixture offline**, run `jpack-runner verify-preparation` with the fixture's dialect (or its unbound document and binding), case, profiles, retained sources and expected preparation, and the preparation's digest supplied apart from the fixture; read `--capabilities` first to learn the versions, kinds, shapes and bounds the command reads. A reading establishes recomputation under the supplied profiles, never the truth of a record; a wrong digest pin is a precondition failure with exit status 3 and no report.
- **To add a model or profile binding to a running installation**, register the profile through the private API; it is persisted before it is exposed, reused ids with changed contents are refused, existing releases keep their pins, and the combined profile limit stays.

## verify-preparation (#117, closing #110; #119; #125, closing #123)

- The command reuses the preparer the vector test uses: the expected file's digest first, then the dialect's and the binding's forms (§4.4), the retained acquisitions under their profiles at the fixture's `verifiedAt` (never the clock), the recomputation and the canonical digest comparison; the report in §11's form, exit status 0 for a reading, 1 for a refusal, 2 for a finding, 3 with no report when it cannot run; a reading's binding is `not-checked`.
- Its forms and finding order are the specification's: counted bounds before any form, every kind's form (the unsupported `http`, `sql` and `web` kinds included) before a kind is refused, a local file's parameters admitted offline, each object held to its kind's member set, the version-2 document digested as given, the acquisitions' checks before the admission findings; it agrees with the specification's Python reader, stdout and exit status byte for byte, on all forty-one vectors and the Exchange catalog's copied fixtures.

## Immutable profile registration (#122)

- The private API accepts a profile registration that is persisted before it is exposed and available to planning and preparation without restarting workers; the same id with changed contents is refused; registered profiles survive restart and can back configured gateway connections; profile reads take immutable snapshots.

## The profile admission's comment (#115, closing #114; #120, closing #116)

- The comment states the class rule as RFC 0018 rounds 13 and 14 do; no behaviour change.
