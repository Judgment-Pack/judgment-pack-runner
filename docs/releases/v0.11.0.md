Runner v0.11.0: a mapping v2 preparation is prepared and verified from a retained record of any gateway adapter shape, `http` and `airbyte` beside `mcp`, and a tenth vector holds it.

## What an operator must do

- **Nothing.** Exports, the journal, `verify-run`'s report, its exit codes and refusal flags are byte-identical to v0.10.0's for every existing run; the nine published vectors recompute byte for byte through this release. No Runtime pin moves: CI keeps Runtime v0.31.0 and v0.27.1.
- **An operator whose gateway offers an `http`-shaped source** (a connection read through `adapter-http`, the Databricks and Azure DevOps connections among them) may now name it in a mapping's `operation` source: the input profile pins the adapter's shape, and the request is the source's form (`{method, path, query}` for `http`), not a tool call. An `http` profile pins the endpoint its receipts name, which for `adapter-http` is the URL asked without its query: one profile per path. An `airbyte` profile is admitted the same way, but the gateway's `adapter-airbyte` returns a page from every read and a paged acquisition is refused as before, so a record from today's adapter is refused for its page, not its shape.

## The preparer over every adapter shape (#80, part of #79)

- `validateProfileKeys` admits a profile of shape `airbyte` beside `mcp`, `http` and `command`; an operation may be read from a profile of any adapter shape, and a bare `command` profile is refused for an operation with a reason naming the three shapes. The record's own `acquisition.shape` must still equal the shape its profile pins.
- The tool-call form of a request (a fixed literal tool the profile allows, an `arguments` object, DBHub's `execute_sql` rule) moved from the profile-free validation into `mcpToolCall`, run only for a profile of shape `mcp`; every request is still held to the template rules and committed to by its receipt; the refusal texts are unchanged.
- The derivation of the retained result, the lineage, the outcomes and the canonical form are untouched: the preparation's bytes do not depend on the source's shape, and `MAPPING-V2.md` says so. The lineage does not carry the shape; it is bound indirectly, through the profile the mapping pins by digest and the receipt each lineage entry cites.
- `vectors/preparation/http-shaped-source`: a tenth vector, recorded from a stand-in endpoint the test serves over TLS on loopback and read as `adapter-http` reads one, with a receipt minted as a gateway mints one under the profile's key; the request `{"method":"GET","path":"/intake/requests","query":{"id":"REQ-7"}}`; `verified-inputs`, binding `matches`, signed and witnessed. The generator wrote the nine earlier vectors again byte for byte. The specification's dialect version 2 reads an `operation` as an MCP tool call only, so its verifier does not read this vector until its version 3 lands (judgment-pack-spec #141); #79 stays open for that.
- `README.md` no longer lists HTTP-shaped profiles as unsupported for unattended inputs; `openapi.json`'s `InputProfile.shape` gains `airbyte`.
