# v0.30.0

Runner v0.30.0 carries one change since v0.29.0: ordinary runs may declare Spec Core
`0.5.0`, the version that adds annotations and value sets (#232, #233).

Nothing changes for a pack that declares `0.2.0-draft` or `0.3.0`: its runs, records and
exports are byte for byte what v0.29.0 produced. One refusal sentence changes, as set out
below. The store schema is unchanged and there is no migration. The Spec's maturity
remains `draft`. This release claims no Extended Runner support.

## Breaking changes

None for a pack that v0.29.0 admitted.

One refusal changes its text. The `invalid_pack` answer for a pack whose `specVersion`
the Runner does not evaluate now reads `This runner evaluates packs that declare
specVersion 0.2.0-draft, 0.3.0 or 0.5.0; this pack declares "<v>"`. A caller that
compares that sentence must follow it. The code and status are unchanged.

## What an operator must do

- **To run Core `0.5.0` packs, pin a Runtime that evaluates Core `0.5.0`:**
  [Runtime `v0.44.0`](https://github.com/Judgment-Pack/judgment-pack-runtime/releases/tag/v0.44.0)
  or later. With an earlier Runtime, a `0.5.0` pack is refused at the release check with
  422 `runtime_core_unsupported`, and no release is saved.
- **Move a pack written to the working selector `0.4.0-draft` by changing its
  `specVersion` to `0.5.0`.** The Runner never admitted `0.4.0-draft` and still refuses
  it, and `0.4.0`, by name. The pack's bytes change, so it is a new release of a new job
  revision, with a new digest.
- The usual care applies before any upgrade: stop Desk and Runner and back up the Jobs
  workspace, including SQLite/WAL, as
  [State and backups](../../README.md#state-and-backups) describes. A store written by
  v0.29.0 opens with no migration.

## Core `0.5.0` on ordinary runs (#232, #233)

- **The declared version selects the evaluator, exactly.** Ordinary preview admits a pack
  that declares `specVersion` `0.5.0` beside `0.2.0-draft` and `0.3.0`. No pack is
  upgraded.
- **The Runtime is asked first.** Before a `0.5.0` pack is written or checked, the Runner
  asks the pinned Runtime for its `version --format json` answer. The pack is admitted
  only when that answer lists `0.5.0` among its `supportedSpecVersions` and carries an
  evaluator capability for exactly `0.5.0` that has no `stage` member and whose
  `supportedProfiles` lists `base`. The answer is read exactly: a duplicated member, or a
  member named as one of these but for case, is not read as a yes. Members the Runner
  does not know are allowed.
- **A Runtime that does not evaluate `0.5.0` is not reported as a defect of the pack.**
  The check is refused with 422 `runtime_core_unsupported`, and the Runtime is never
  given the pack. Packs under the other versions are not asked the question.
- **Runs and records.** Runs use the release's digest-pinned Runtime. Its answers, the
  release-test report and the audit record must name `0.5.0`, and `verify-run` refuses
  `evaluator-spec-mismatch` otherwise, as for the other versions. No record member is
  added.
- **Value sets and annotations.** The Runner reads no pack conditions itself. Fact
  coverage comes from the Runtime, and a fact path a pack reads only through a value set
  is counted. Annotations do not change a decision, and the Runner does not read them.
- **The selected retained-column path stays on `0.3.0`.** Its companion is written
  against Core `0.3.0`, and a `0.5.0` pack on that path is refused by name with 422
  `invalid_pack`.
- **The manual profile stays on `0.2.0-draft`,** as before.

## What this release does not establish

- **No conformance claim for Core `0.5.0`.** The Runtime reads the `base` profile only
  and makes no conformance claim for `0.5.0`; the Runner adds none.
- **Workflow stages (#234).** In a workflow stage whose pack declares a Core other than
  `0.2.0-draft`, a Core evaluation error is recorded as an interrupted attempt, not as a
  failed one. Nothing is invented and the run does not complete. This has applied to
  `0.3.0` since v0.27.0.
- **An answer with two entries for `0.5.0`.** A version answer that carries two evaluator
  entries for `0.5.0` is admitted if one of them qualifies. The Runtime writes one entry
  for a version.

## Verified with

Main CI at the tagged commit builds and runs against these commits
(`scripts/checks/build-pinned.sh`). None moved since v0.29.0, and one is new.

| Companion | Commit | Release |
|---|---|---|
| Tested Runtime | `09206e7` | main at runtime #291, contained in v0.38.0 |
| Retained-column Runtime | `12793d2` | v0.39.0 |
| `packs covers` Runtime | `6a210ac` | v0.41.0 |
| Core `0.5.0` Runtime (new) | `8955c9f` | v0.44.0 |
| Earlier Runtime | `7a2fcfe` | v0.27.1 |
| Durable Gateway contract | `82d4f8a` | v0.23.0 |
| Old Runner | `1cc6b29` | test-only |

The Spec pins are unchanged. The `0.5.0` test pack is written by hand against Spec
`v0.5.0`.

The Core `0.5.0` tests run against the pinned Runtime v0.44.0: the three Core versions
side by side in one service, signed runs, export and `verify-run`, restart and restore
from a backup. The refusal is tested against the tested Runtime and the retained-column
Runtime, neither of which evaluates `0.5.0`. The CI step after the tests fails if any of
these did not run and pass.

Desk is not pinned by this release; Desk adopts it in its own lane.
